# Python to Rust Migration Plan

## 结论

本项目全部代码迁移到 Rust 在技术上可行，但不建议一次性重写并直接替换。当前项目同时包含离线 ZIP 重构、JSON/YAML 处理、图片文件操作、SQLite 标注复用、Excel 读写、命令行交互和本地 Web 审核界面。Rust 适合承担计算、压缩、数据库和文件处理，但一次性迁移会带来较大的行为回归风险。

当前执行范围只包含 SQLite 数据库按 `stationSN` 拆表。Rust 迁移暂不实施，继续使用已经验证的 Python 代码。

## 当前功能边界

| 功能 | 当前实现 | Rust 可行性 | 迁移风险 |
| --- | --- | --- | --- |
| 外层 ZIP 和内层 ZIP 解压、归并、重打包 | Python `zipfile` | 可行 | 中 |
| `accuracy.json` 结构化解析和重写 | Python JSON | 可行 | 低 |
| YAML 配置读取和任务时间更新 | Python YAML | 可行 | 中 |
| 图片复制、重命名、目录输出 | Python 文件 API | 可行 | 中 |
| SQLite 标注历史和按站点子表 | Python `sqlite3` | 可行 | 低 |
| Excel 清单读写 | `openpyxl` | 可行，但库选型需要验证 | 高 |
| 本地 Web 审核 API 和静态页面 | Python HTTP 服务 | 可行 | 高 |
| Windows 命令行、批处理和本地部署 | `.bat` + Python | 可行 | 中 |

## 推荐架构

采用分层迁移，不改变业务输入输出格式：

1. Rust 核心库负责 ZIP、JSON/YAML、图片文件和 SQLite。
2. Rust CLI 提供批处理入口，输出与现有 Python CLI 一致的文件和日志。
3. 审核 Web 页面先保持不变，使用 HTTP 调用 Rust 服务或 Rust CLI。
4. Excel 先由 Python 兼容层负责，待 Rust Excel 库通过样本和回归测试后再迁移。
5. Python 与 Rust 并行运行一段时间，使用相同输入包比较 JSON、图片、ZIP 成员和数据库结果。

## 分阶段实施

### 阶段 0：建立基线

- 固定一批真实 ZIP、配置文件和历史数据库副本。
- 保存当前输出 ZIP、`accuracy.json`、图片数量、文件名和日志摘要。
- 记录处理耗时、峰值内存和数据库导入耗时。
- 将现有 Python 测试扩展为输出级回归测试。

验收：同一输入重复运行结果稳定，基线文件可以自动比较。

### 阶段 1：迁移数据库和纯数据核心

- 实现 Rust SQLite 访问层。
- 保持 `station_index` 和每个 `stationSN` 子表的 schema 不变。
- 实现 JSON/YAML 解析、标注复用、排序、图片复制和重命名。
- 保留 Python Web 审核界面，通过命令或 HTTP 调用 Rust 核心。

验收：Rust 与 Python 对相同输入生成等价标注结果，`testCode` 始终不写入数据库。

### 阶段 2：迁移 ZIP 重构流水线

- 实现外层包解压、内层包配对、归并、元数据更新和重打包。
- 对压缩包成员、路径穿越、损坏文件和重复图片名做回归测试。
- 增加并发时只在独立任务或独立文件上并行，数据库写入仍使用事务。

验收：输出外层 ZIP 只包含预期内层 ZIP，JSON、图片和 YAML 引用全部一致。

### 阶段 3：迁移审核服务和 Excel

- 评估 Rust Web 框架和现有前端接口兼容性。
- 对 Excel 读写库验证合并单元格、样式、公式、中文工作表名和表格对象。
- 只有在兼容性和输出回归测试通过后才替换 Python 实现。

验收：审核流程、导出清单和用户可见结果与 Python 版本一致。

### 阶段 4：切换和回滚

- 默认继续保留 Python 入口，增加可配置的 Rust 入口。
- 先小批量启用 Rust，比较失败率和耗时。
- 保留 Python 版本和数据库备份，出现差异时可立即回退。
- 连续一段稳定运行后再删除重复实现。

## Rust 技术选型方向

- JSON：`serde`、`serde_json`
- YAML：`serde_yaml`
- SQLite：`rusqlite`
- ZIP：成熟 ZIP 读写库，并为损坏成员和路径安全编写测试
- 并发：优先使用任务级并行；需要异步 HTTP 时再引入 Tokio
- Web：使用与现有 API 路径和 JSON 契约兼容的 HTTP 框架
- Excel：先做候选库验证，不在没有样本回归的情况下替换 `openpyxl`

## 主要风险

1. Rust 和 Python 的 JSON/YAML 类型转换可能改变空值、数字或字段顺序处理。
2. ZIP 条目编码、文件名大小写和 Windows 路径行为可能不同。
3. Excel 样式和表格对象兼容性比普通数据读写更难保证。
4. 并发写 SQLite 不能简单地把所有请求并行化，需要明确事务边界和忙等待策略。
5. 本地 Web 审核依赖现有前端行为，接口字段和错误码必须保持兼容。
6. Rust 二进制在目标 Windows 环境的打包、运行库和日志路径需要单独验证。

## 是否值得迁移

建议迁移，但采用“Rust 数据处理核心 + Python 审核兼容层”的过渡架构。预计主要性能收益来自 ZIP、JSON、图片和批量数据库处理；如果瓶颈主要是人工审核 Web 流程或 Excel 生成，全量 Rust 重写的收益会低于维护成本。

在阶段 0 完成基线前，不应承诺具体加速倍数。只有当 Rust 版本在输出一致性、错误处理和部署方式上通过回归测试，且实际耗时明显改善，才进入默认切换。
